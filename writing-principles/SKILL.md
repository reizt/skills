# 文章の共通原則

場面ごとのスキルがこの原則と食い違うときは、場面のスキルを優先する。

## 基本原則

読み手のペルソナ（知識状態・関心事）を設定し、その文章・単語だけで伝わるかを抜かりなくチェックする。
ペルソナは、足りない説明だけでなく多すぎる説明の判定にも使う。
読み手がもう知っていること、自分で補えること、後で参照しない固有名は書かない。

一番伝えたいことが一文目でわかるようにし、その文章は単体で読み手に意味が通るものでないといけない。
番号だけ、または「こちら」だけで参照しない。参照先が何なのかを一句添える（「#1111(顧客制限の表示)」「[変更方針整理 1-4 の結論](url)」）。

推測したもの・未確認のものは明記する。

## 文の分け方

接続助詞（「〜し、」「〜ので、」「〜が、」）で文を長くつなぐより、文を分けて改行し、文頭の接続詞（「そのため」「ただし」「一方で」）で展開をつなぐ。

悪い例：
API の仕様が変わったので、クライアントの修正が必要だが、リリースは来週なので、今週中に対応する。

良い例：
API の仕様が変わった。
そのため、クライアントの修正が必要になる。
リリースは来週なので、今週中に対応する。

ただし、目的や理由が文末の結論にかかっている文（「〜するために〜する」）は分けない。
分けると、何のために何をするのかの向きが変わる。

短く削るときは、まず単体で通じる文を書き、次にリンク先でわかる説明を削る。
逆の順で書くと削りすぎて、単語が浮く。

## レイアウト

不要な補助ラベルや補足説明は避ける。レイアウト自体に語らせる（説明させる）のが理想。
文章のレイアウトに CRAP 原則を適用する。

- **Contrast**：他と違うもの・注意が必要な単語や文節や文を目立たせる
- **Repetition**：フォーマットを一貫させる
- **Alignment**：適切に改行するなどして、似た要素が同じ位置から始まるようにする
- **Proximity**：関連する情報をまとめて、他と間隔を空ける

## 語句選び

語句の詳細度は、それが指したい概念の詳細度によって調整する。
たとえば、テーブルのカラムを明示したいときは「`user` テーブルの `name` 列」と言えばいいし、抽象的なリレーションを指す場合は「ユーザーの名前」というべきだ。

動詞や形容詞にも言い換え表現は複数考えられるが、その中でも「誤解を招かない最も平易なもの」を選ぶ。

一度決めた呼び名は最後まで通す。
呼び名は正となる資料（仕様 wiki、設計ドキュメント）に揃える。
内部で作った用語は初出で定義し、多義語は意味を限定する（「契約」→「OpenAPI 契約」「顧客の契約」）。
