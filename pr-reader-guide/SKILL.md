## 概要

実装のPRを対象として、**PRの本文とインラインコメントでの説明によって、レビュアーのレビュー負荷を最小化する**ためのスキル

## 前提

実装PRにおけるレビュイーの責務は、以下2つをレビュアーに理解させることである。

- 変更意図は何か
- 変更意図に対してなぜその実装をしたのか

また、1つのPRに複数の変更意図を含めてはいけない。
以下の2つが同一のPRに混じってはいけないし、全く違う振る舞いの変更/構造の変更が2つ以上含まれることも許されない。

1. 振る舞いの変更 ... ユーザーから見た振る舞いが変わる。
2. 構造の変更 ... ユーザーから見た振る舞いは変わらない。

## レビュアーのペルソナ

知っていること：

- リポジトリのユビキタス言語
- リポジトリのアーキテクチャ
- すでに確定した設計・方針・仕様（ドキュメントの内容）

知らないこと：

- どの実装がどの変更意図に対応しているか
- 実装中に作者が下した、事前のドキュメントに無い判断
- 過去 PR の経緯
- 作者が内部で作った用語

読む順番：

1. 本文を見て、変更意図と変更範囲を理解する
2. 変更のファイルツリーを見て、違和感のあるものを読み、違和感を解消しにいく。解消されなければまずコメントする
3. 次に、コメントとファイルツリーを一通り見て、読むべき対象を絞る
4. 次に、主要な部分を読み、コメントで実装判断の根拠を理解し、異論があればコメントする
5. 他に見落としている変更がないか見る

## 本文とインラインコメントの役割

- 本文：PRの変更意図と変更範囲を最短で理解させること
- インラインコメント：なぜその変更が必要なのかを説明すること

## 本文の書き方

変更意図によって、パターンが分かれる。

### 1. 振る舞いの変更の場合

以下のフォーマットを例として AS-IS/TO-BE を記載する。

```md
## AS-IS/TO-BE

| AS-IS                      | TO-BE                      |
| -------------------------- | -------------------------- |
| どんな振る舞いだったか     | どんな振る舞いになったのか |
| どんな課題が生じていたのか | どんな価値が得られるのか   |

### UIキャプチャ(画面要素に増減がある場合)

<2列の表>

### シーケンス図(表示だけでなく、ユーザーフローが変わる場合)

<シーケンス図2枚>
```

### 2. 構造の変更の場合

```md
## AS-IS

- どんな振る舞いだったか
- それによって、どんな課題が生じていたのか

## TO-BE

- どんな振る舞いになったのか
- どんな価値が得られるのか

## シーケンス図(処理フローが変わる場合)

<シーケンス図2枚>

## 依存関係図(依存関係が変わる場合)

<有向グラフ2枚>
```

## インラインコメントの書き方

変更意図に対してなぜその実装が必要なのかを説明する。
実装から一目で読み取れる自明なことは説明しない。

### 違和感の解消

- 本文で説明した変更範囲に一見含まれない部分は、判断を含まないこと・品質に影響しないことを説明し不安を先回りして解消する

### 実装判断の説明

- 設計時と比べて具体化した処理条件を説明する。
- 棄却案がある場合は棄却理由を簡潔に説明する。大体「採用案のメリットが大きい」「棄却案のリスク・デメリット・コストが大きい」のどちらかで説明がつく

**Practices**

APIの振る舞い変更の例。フォーマットの原則は $writing-principles が正本。

```
リクエストに〇〇が指定された時の〇〇の導出方法を、設計時から具体化した。

**設計時**

〜〜

**実装時**

〜〜

```

## Runbook

- 本文・インラインコメントともに、文章の書き方は $writing-principles に従って**徹底的に**見直すこと
- コメントの作成・更新・削除は $pr-comments の pending review の手順で行う
- 本人がレビュー対応で commit を積んだら、判断が変わったコメントは文面も直し、ドキュメント側の追記へリンクする。
  - 位置がずれた行コメントの付け直しは $pr-comments の手順で行う。
- レビューを submit しない。approve / request changes もしない
- 本人が UI で書いたコメントや返信を上書きしない
