name: small-refactors
description: Doing small refactors
---

## 方針

- 過剰にやりすぎないこと
- 振る舞いの変更をするPRで影響範囲外の整頓を行わないこと

## 実践例

1. early return
2. デッドコードの削除
3. シンメトリーを揃える = 同じことは同じ書き方に
4. 理想のI/Fを定義して、内部で古い実装を呼び出す
5. 読み手が出会いたい順に並べる
6. 凝集度を上げる = 共通化ができなくても、隣に置くだけで効果がある。コストとの兼ね合い
7. 宣言と初期化を一緒に
8. 説明変数 = 長い式の一部を、意図がわかる名前の変数にする。苦労して掴んだ理解をコードに残す
9. マジックナンバーを定数化する
10. パラメータを明示的に
11. 意味の切れ目に空行を入れる
12. 目的で名前をつけてヘルパーを抽出する
13. 分けすぎてわからない時はインライン化してみてから分け直す
14. なるほどと思った瞬間にコードから読み取れないことをコメントで書く
15. 冗長なコメントを削除する

## 完了時

適用後（見た結果リファクタ不要と判断した場合も含む）、次を実行して pre-commit hook に実施済みを伝える。commit するたびに HEAD が進むので、commit ごとに再度通す。

```bash
git rev-parse HEAD > "$(git rev-parse --git-dir)/small-refactors-ok"
```

## すぐ使えるおすすめリファクタ

- `if (~~)` を説明変数に使って `if (isXxx)` にして、early return
- 関数のコードコメントは「〇〇を受け取って〇〇を返す関数」の1行にして、それ以上はコードから読み取れないことがある場合だけ補足
- 関数の呼び出し元の知識がコメントに混じらないようにする。コメントも関心の分離が大事。
